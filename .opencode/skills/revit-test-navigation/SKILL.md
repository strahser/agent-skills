# Навигация по тестам и учёт золотых чисел

Цель: агент (и владелец) должен ответить на «где тесты по блоку», «какие тесты охраняют D-решение»
и «кто владелец пина» **одним поиском**, а не грепом по 700 файлам.

## Когда использовать

- Нужно найти тесты по бизнес-блоку или по номеру решения канона (D25, D36.1, C-0…).
- Нужно понять, откуда взялось «золотое число» и что чинить при дрейфе.
- Перенос/переименование тестовых файлов, добавление папок и меток.
- Перед отчётом сессии: обновить карту `TESTS-MAP`.

## Когда не использовать

- Оценка одного теста (точность ассертов, RED→GREEN) → `revit-test-quality`.
- Запуск тестов в Revit, потоки, исполнитель → `revit-testing`, `revit-test-runner`.
- Документы и данные кейсов → `revit-test-fixtures`.

## Правило 1 — Папка = бизнес-блок, не слой

Раскладка по фичам (эталон HeatLossRevit4):

```
Core.Tests/     01-Snapshot  02-OmBuild  03-Calculation  04-Externality  05-Reports
                06-Pipeline  07-Linking  08-Geometry     09-Valves       10-Licensing
                99-Infrastructure
Modeling.Tests/ 01-Modeling  02-OpeningArea  03-ViewModels  04-Sp50  99-Shared
Live tests/     Live/Om   Live/Integration   Live/Probes   Live/Infra
```

- В каждом блоке — `README.md` на 5–15 строк: что за блок, какие D-решения охраняет, какие пины,
  какие живые тесты. Блок без README считается неоформленным.
- Не дробить мельче: блок меньше ~10 файлов — это файлы «в общем», лучше в `99-*`.
- Папка ≠ namespace: перенос файла `git mv` не требует правок кода (C# это допускает).

## Правило 2 — машинные метки (`[Trait]`), а не пути

```csharp
[Trait("block", "04-Externality")]   // папка-блок
[Trait("canon", "D25")]              // решение канона, если тест его охраняет
[Trait("layer", "core")]             // опционально: core / revit / ui / live
public class WallExternalDeterminerTests { ... }
```

Фильтры (не зависят от пути файла, переживают переезды):

```powershell
dotnet test Core.Tests\Core.Tests.csproj -c Release --filter "block=04-Externality"
dotnet test Core.Tests\Core.Tests.csproj -c Release --filter "canon=D25"
```

Один класс может иметь несколько `canon`-меток. Если класс охраняет решение — ставить метку **там же,
где меняется ассерт**; метка без теста запрещена.

## Правило 3 — реестр золотых чисел (GOLDENS)

Один файл в репозитории планов: `_reference/GOLDENS-<дата>.md`, таблица «пин | значение | тест-владелец | смысл».

> В HeatLossRevit4 актуальный эталон — `_reference/TESTS-METRICS-CARD-2026-11-07.md`
> (40/80/212/39/5, 305/452, Q 86071,03/82077,99, 105/105 и 104/88). `GOLDENS-2026-11-03.md`
> оставлен историческим: 76/102/249/Q 87063,6 после `e20ca123`/`f0aac375` недействительны.

При дрейфе:
1. Открыть GOLDENS и найти пин.
2. Пойти в его тест-владельца.
3. Чинить **код**, а не ожидание (кроме случая, когда решение владельца изменилось явно).
4. Меняется пин → в том же коммите обновить GOLDENS и карточку/канон.

## Правило 4 — карта тестов

`Tools\test_map.ps1` (пишет `_reference/TESTS-MAP.md` и `.csv`) собирает:
папка → классы → число `[Fact]/[Theory]/[Test]` → `[Trait]`. Обновлять перед отчётом сессии.
Скрипт только читает исходники, тесты не запускает.

## Правило 5 — перенос тестов безопасен, если соблюдены 4 условия

1. Только `git mv` (история сохраняется).
2. **Инвариант счётчиков:** сумма `[Fact]+[Theory]+[Test]` по проекту до и после — одинаковая.
3. `dotnet test <проект> -c Release` — 0 failed после каждого батча; для живых — сборка проекта.
4. **Пути в тестах-гардах** правятся в том же коммите. Искать заранее:
   `Select-String -Path **\*.cs -Pattern 'Core\.Tests/|Modeling\.Tests/'`
   (эталон: `FixtureDuplicationGuardTests.AllowedManualSweepFiles` / `AllowedLoggerFiles`).

Один батч = один блок = один коммит.

## Правило 6 — метки в прод-коде для графа

Владельцу нормально, что код пишется с ИИ; метки не прятать:

```csharp
// @canon D25 — контурный путь зон (решение владельца 24.10.2026)
// @owner планировщик; @since 2026-11-03
public sealed class PlanGlobalContour ...
```

- `@canon Dxx` — решение, которое реализует метод/класс; даёт связь «код ↔ канон ↔ тесты».
- `@since` — когда появилось (для аудита свежести).
- Не заменять метками комментарии о смысле; имена — ASCII (в проекте есть гард `check_identifiers_ascii`).

## Чек-лист перед коммитом раскладки

- [ ] счётчики до/после совпали;
- [ ] тесты зелёные; живые собираются;
- [ ] новый блок имеет `README.md` и `[Trait("block")]` у всех классов;
- [ ] allow-list гардов обновлён (если переезжали их файлы);
- [ ] `TESTS-MAP.md` пересобран, если менялись папки/метки.
