Ты — аудитор кодовой базы, который ищет **не мёртвый код, а «ненужные цепочки»**: код,
который жив (есть вызовы, DI-регистрации, тесты, doc-комментарии), но по сути
**бесполезен или вреден**. Типовой пример владельца: «снимок АР не найден → давай получим
данные из…» — вместо честной валидации начинается фантазия.

## Когда использовать

- Аудит архитектуры/долга перед крупным рефакторингом C#-решения (net48, Revit-плагин).
- Поиск фолбэков, которые подменяют отсутствие валидации.
- Ревизия настроек: «какие настройки реально управляют поведением».
- Подготовка плана блоков правок «один блок = один коммит» + вопросов владельцу.

## Когда НЕ использовать

- Точечный багфикс без архитектурного влияния.
- Нужно **править** код, а не описать состояние (этот скил read-only).
- Нет документа-источника истины по поведению (см. Шаг 0) — сначала заведите его,
  иначе вердикты будут вкусовыми.

## Главный вывод (проверено на аудите HeatLossRevit4: 26 находок, 9 из них критичные)

**Основной инструмент аудита — не граф кода, а матрица «решение владельца → код».**
Граф описывает **структуру**, а «ненужная цепочка» — это расхождение кода с **намерением**.
Именно поэтому такой код и «не мёртвый»: граф честно говорит «метод вызывается из 8 мест» —
и это правда, которая и есть ловушка.

| Инструмент | Что реально дал на аудите |
|---|---|
| Матрица «решение владельца → реализация → тест → вердикт» + чтение цепочек | **9 из 9 критичных находок** |
| Шаблонный grep + трассировка до потребителя | адреса и «живость» ещё ~12 цепочек |
| Граф Roslyn (MCP) | **измерения** и **read/write-аудит** (поле, которое никто не пишет; настройка, которую никто не читает) |
| ast-grep | ноль находок (структурный поиск — для правок, не для аудита смысла) |

Не начинай с графа. Начинай с контракта.

## Метод (по шагам)

### Шаг 0. Источник истины = намерение

Найди документ с **решениями владельца** (в проектах конвейера — `BUSINESS-LOGIC*.md`
§14.4 + контракты §10–§13 + §15 «известные расхождения»). Если его нет — первый
артефакт сессии это он, а не отчёт.

Правило проекта: **расхождение кода с решением владельца — это баг**, но молчаливая
правка запрещена; поведение меняется только по решению владельца + тест-приёмка.

### Шаг 1. Матрица «решение → реализация → тест → вердикт»

Построй построчно по каждому пункту решений. Колонки:
`пункт | требование кратко | реализация (файл:строка) | тест-гард (класс/метод) | вердикт`.

Вердикты: `соответствует` / `расходится` / `частично` / `не проверяемо headless` (+почему) /
`устарел-снять`.

Это самый дорогой и самый результативный шаг. Полезно распараллелить субагентами:
один агент — контракты, другой — решения владельца; каждый пишет **файл-фрагмент**
(`_audit-parts/matrix-*.md`), родитель вклеивает.

**Обязательно проверяй не только «работает ли механизм», но и все его потребители.**
Урок аудита: пункт «поиск не влияет на расчёт» был закрыт и проверен — и всё равно
оказался расхождением, потому что поиск влиял на **экспорт отчёта** (цепочка
`ViewModel → synchronizer → DetailedViewModel._allData → ExportActions`). Проверка была
верной, но неполной.

### Шаг 2. Шаблонный grep по фолбэкам

Ищи не «мёртвый код», а признаки подстановки чужого источника:

```
[Ff]allback | Фолбэк | аварийн | запасн
\?\?\s*(new|Get|Default|Empty|Instance)          # ?? new Settings()
catch\s*\([^)]*\)\s*\{\s*\}                      # пустой catch
OrderByPreference | FirstOrDefault.*(snapshot|level|room)   # выбор «первого пригодного»
\?\?\s*new\s+(List|Dictionary)<                  # защита от null — обычно безобидна
```

Для каждого совпадения **обязательна трассировка до потребителя**: кто вызывает, что
делает с результатом, что увидит пользователь. Без трассировки вердикт не выставляется —
именно трассировка отделяет 🔴 от ⚪.

### Шаг 3. read/write-аудит полей и настроек (граф)

Тут граф объективно сильнее человека. Для каждого подозрительного поля/настройки:

- `find_references(symbol, kinds: ["write","readwrite"])` — кто **пишет**;
- `find_references(symbol)` — кто **читает**.

Два реальных улова:
- поле пишут **только тесты**, а прод читает как значимое → ветка в проде невыполнима;
- настройка имеет 2 ссылки, обе в UI → расчёт её не читает, «мёртвая настройка».

Это закрывает класс «мёртвые/перекрытые настройки и поля-сироты» механически, без чтения.

### Шаг 4. Измерения (граф), а не оценки

Что снимать обязательно — иначе отчёт будет вкусовым:

| Инструмент | Зачем |
|---|---|
| `find_god_objects` | типы, где **размер и связность** превышены одновременно |
| `get_complexity_metrics` (cyclomatic + cognitive) | методы-монстры; cognitive важнее для читаемости |
| `find_catch_blocks` | сколько `catch (Exception)` и сколько **без `throw`** |
| `find_async_violations` | `async void`, sync-over-async (`.Result`/`.Wait()`), fire-and-forget |
| `find_disposable_misuse` | кандидаты в утечки (учитывай ложные: Revit `Element`/`Parameter` не `IDisposable`, а `Options`/`CurveLoop` — да) |
| `find_unused_symbols` | **кандидаты**, не приговор: XAML/DI/рефлексия не видны графу |
| `find_circular_dependencies` | циклы проектов/namespace |
| `get_project_health` | сводка по проектам одним вызовом |

### Шаг 5. Вердикт каждой цепочке

Классифицируй **по последствию**, а не по типу кода:

| Метка | Признак | Пример из аудита |
|---|---|---|
| 🔴 портит данные молча | подставляется **другой источник**; пользователь видит «успех» | нет снимка связанного АР → берётся «свежайший» снимок другого здания, предупреждение не срабатывает |
| 🔴 | вшитые в сборку тестовые/чужие данные как «дефолт» | нет файла БД → возвращается вшитый дамп чужого проекта |
| 🔴 | безусловная перезапись пользовательского значения | зонный k перекрывает ручной k из модели |
| 🟠 скрывает отказ | `catch` → строка в лог, расчёт продолжается | `catch` вокруг мёржа БД вместо блокирующей ошибки |
| 🟠 | разные причины отказа схлопнуты в одну неверную реплику | 4 причины «ОМ не построена» → текст «нет DirectShape-стен» |
| 🟠 | фолбэк молча отключает сервис | репозиторий не поднят → `null` без лога → «0 клапанов» |
| ⚪ живое, но бесполезное | обвязка есть, эффекта нет | метод извлечения температур не вызывается; словарь всегда пуст |
| ⚪ | настройка, которая не влияет | допуск из UI не читается расчётом |
| ⚪ | поле, которое никто не пишет | пишут только тесты, прод читает |
| 🟢 образец | фолбэк **громкий** и посчитанный, либо отказ вместо фантазии | счётчик `ThinFallbacks` + Error-лог; «данных нет → orphan для диагностики» |

**Обязательно найди и процитируй 🟢-образцы того же проекта** — это готовый шаблон для
блоков правок и защита от «давайте всё перепишем».

### Шаг 6. Артефакты

1. `REPORT-<дата>-<тема>.md` — измерения «до», границы слоёв, карта цепочек, вердикты
   по всем контрактам и открытым пунктам, план блоков правок.
2. `QUESTIONS-<дата>.md` — вопросы владельцу **с вариантами A/B/C, рекомендацией и полем
   ответа**. Вопрос обязателен там, где правка меняет поведение или golden-числа.
3. План блоков: `блок | привязка к решению | гард/тест | приёмка | риск | оценка`.
   Порядок — от «дёшево и без риска» (механические гарды, мёртвый код, тексты) к
   «дорого и с поведением» (golden под стоп-контролем).

Правки кода в аудит-сессии не делаются, если владелец не сказал иначе: коммиты — по его команде.

## Грабли (реальные, из сессии)

- **PowerShell и кириллица.** `Get-Content` + `Set-Content` на UTF-8 файле с русским
  текстом портят его двойным кодированием (UTF-8 прочитан как CP1251). Для склейки
  больших markdown-артефактов использовать только
  `[System.IO.File]::ReadAllText/WriteAllText($p, $t, (New-Object System.Text.UTF8Encoding($false)))`.
  Признак порчи: `РњР°С‚СЂРёС†Р°`; лечится обратным преобразованием
  (`Encoding.GetEncoding(1251).GetBytes(s)` → `UTF8.GetString(bytes)`), но часть
  символов теряется — лучше не доводить.
- **Правка markdown якорем.** Заменяя заголовок-якорь через edit, **не теряй сам
  заголовок** — в новом тексте он должен остаться (иначе раздел «съедает» следующий).
- **Не дампить ответы MCP в контекст.** `get_project_health` ≈ 40 КБ, `find_unused_symbols`
  ≈ 800 записей; широкий шаблон ast-grep однажды вылил 705 КБ. Ставь `limit`, сужай
  `paths`, а громоздкое сохраняй в файл и читай точечно.
- **ast-grep MCP:** абсолютные пути **отклоняются** («Path must be relative»), рабочий
  каталог сервера = корень проекта, относительные пути — от него; язык C# — `cs`/`csharp`,
  методы искать через `selector: method_declaration`; без `AST_GREP_BIN` обёртка падает.
- **`roslyn_graph` холодный старт** открывает решение 30–60 с (один раз был `disconnected`,
  клиент переподключился сам). Первый вызов после старта сессии — терпеливый.
- **Тест — не всегда гард.** Тест может **пинить вредный фолбэк**
  (пример: `OrderByPreference_NoMatch_SortsByFreshness` закреплял подстановку чужого снимка).
  В матрице так и пиши: «гард есть, но гардирует расхождение».
- **Живой код ≠ нужный код.** `find_references` = 0 ссылок — это ⚪-находка, но её
  «бесполезность» видна только при чтении: рядом может лежать doc-комментарий, обещающий
  работу, которой нет.

## Инструменты и настройка

MCP-серверы графа кода для DSH (установка, конфиг, что отдают, отброшенные кандидаты):
см. вики `agent-skills\.opencode\wiki\mcp-code-graph.md`.
Для opencode — `mcp-setup`.

Минимальный набор для аудита C#: **`roslyn_graph`** (Roslyn, семантика) — обязателен;
`astgrep` — только под структурные правки, для аудита смысла бесполезен.

## Чек-лист перед сдачей

- [ ] Матрица покрывает **все** решения владельца и открытые пункты, без «пропущено».
- [ ] У каждой находки — `файл:строка`, что именно подставляется, какой пункт нарушается
      и **что произойдёт с пользователем молча**.
- [ ] Каждая цепочка трассирована до потребителя (иначе вердикт не выставляется).
- [ ] Измерения «до» приведены числами (не «много»), с указанием инструмента и метода.
- [ ] Есть 🟢-образцы из этого же проекта.
- [ ] Поведенческие правки вынесены в вопросы владельцу (A/B/C), а не в план «молча».
- [ ] Обновлены: план проекта, раздел «известные расхождения», гайд агента (если менялись правила).
