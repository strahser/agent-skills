# Задание для облачного ИИ: архитектура BIM-проекта (Revit) — ядро + операции + JSON-стандарт

**Статус:** черновик ТЗ, ожидает проработки облачным ИИ и утверждения владельцем.
**Автор запроса:** владелец (Страхов), проекты: HeatLossRevit*, RevitHeadless (К1 библиотека), MepBimServer, MepTaggingSolution, DwgParser.
**Дата:** 2026-11-03.

## 1. Контекст и текущее состояние

Сейчас работа с Revit ведётся набором разрозненных скриптов и тестов:

- `RevitHeadless/K1LibraryTests.cs` — монолитный тест-скрипт, который читает JSON-контракт (`K1_library_linked.json`) и строит модель (уровни, оси, стены, проёмы, кровля, стропила, дефекты). Вся логика в одном классе, смешаны: чтение JSON, транзакции Revit, геометрия, отчётность.
- `HeatLossRevit4/` — отдельный проект с собственными скриптами/тестами, дублирует часть паттернов (создание стен, работа с уровнями).
- `MepBimServer`, `MepTaggingSolution`, `AHUCalculator` — каждый со своей логикой.
- Данные хранятся в разных форматах: JSON-контракты (K1), входные DWG/DXF, xlsx-спеки, PDF. Нет единого стандарта схемы.
- Нет переиспользуемого ядра: транзакции, работа с уровнями/осями/стенами, загрузка семейств, откаты — копируются из проекта в проект.
- Тесты (Nice3point.TUnit.Revit) запускаются только в Revit, смешивая проверку логики с проверкой API.

Цель: превратить набор скриптов в **расширяемый проект с ядром, набором операций и стандартом хранения данных**, чтобы новые проекты (К1, коровники, МКД) добавлялись без копирования логики.

## 2. Цели

1. **Ядро** (`Core`): абстракции над Revit API — документ, транзакции, уровни, оси, стены, типы стен, семейства/экземпляры, единицы измерения, откаты, логирование. Ядро не знает о конкретных проектах.
2. **Операции** (`Operations`): атомарные, параметризованные действия (`CreateWall`, `CreateWallType`, `LoadFamily`, `PlaceFamilyInstance`, `CreateLevel`, `CreateGrid`, `CutOpening`, ...). Каждая операция: входные DTO, валидация, выполнение в транзакции, результат с handle/Id и диагностикой.
3. **Разделение логики и тестов**: бизнес-логика (валидация, расчёт геометрии, маппинг JSON→DTO) вынесена в чистые функции/классы, тестируемые без Revit; интеграционные тесты (Nice3point) проверяют только слой адаптера.
4. **Расширяемость**: новые проекты добавляются как модули/папки с собственными данными и скриптами, использующими общее ядро. Регистрация операций через реестр/плагины.
5. **Стандарт хранения данных (JSON)**: единая схема для описания здания/проекта, версионирование, валидация, round-trip (JSON → модель → JSON).
6. **Идемпотентность и безопасность**: повторный прогон не дублирует сущности; dry-run; бэкап перед записью; откат по транзакции.

## 3. Требования к ядру

### 3.1. Состав

- `IDocumentContext` / `IRevitContext` — абстракция над `Document`, `UIApplication`, единицами. Должна позволять мокать в юнит-тестах.
- `ITransactionRunner` — запуск транзакции с именем, откат при исключении, вложенные транзакции/группы (SubTransaction), логирование.
- `IUnitConverter` — мм↔футы, градусы↔радианы, консистентные константы (сейчас `MM = 1.0/304.8` разбросан).
- `ILevelService`, `IGridService`, `IWallService`, `IFamilyService` — сервисы по доменам.
- `ILogger` — структурированные логи (уровни, контекст операции, handle/Id результата).

### 3.2. Правила

- Ядро **не содержит** проектной логики (имён уровней, координат, типов стен конкретного здания).
- Ядро **не бросает** Revit-специфичные исключения наружу без обёртки; предоставляет `Result<T>` / `OperationResult` с диагностикой.
- Все координаты/размеры в ядре — в футах (единицы Revit); конвертация из мм — на границе (DTO/маппер).
- Потокобезопасность: операции выполняются в главном потоке Revit (через executor), ядро не создаёт потоки.

### 3.3. Тестируемость

- Вся бизнес-логика (валидация JSON, расчёт точек, выбор типа стены) — в чистых классах без зависимости от Revit API.
- Интеграционные тесты (Nice3point.TUnit.Revit) покрывают только адаптер: «даны DTO → в модели появились ожидаемые сущности».
- Юнит-тесты (обычный TUnit/xUnit) покрывают логику без Revit.

## 4. Требования к операциям

### 4.1. Контракт операции

Каждая операция реализует интерфейс:

```
IOperation<TInput, TResult>
  - Name: string
  - Validate(input, context) -> ValidationResult
  - Execute(input, context) -> OperationResult<TResult>
  - Rollback(result, context) -> void (опционально)
```

- Вход: DTO (record/класс) с явной схемой.
- Выход: `OperationResult` с `Success`, `CreatedIds` (ElementId/UniqueId), `Warnings`, `Diagnostics`, `Duration`.
- Валидация до транзакции: отсутствующие уровни, несуществующие типы стен, пересечения — возвращаются как ошибки без изменения модели.
- Операция не вызывает другие операции напрямую; композиция — на уровне оркестратора/скрипта проекта.

### 4.2. Базовый набор операций (MVP)

Уровни/оси: `CreateLevel`, `CreateGrid` (прямолинейная/дуговая), `CreateGridIntersection`.
Стены: `CreateWallType` (по структуре слоёв), `CreateWall` (линейная/дуговая, по двум точкам или по оси+длина+угол), `CreateWallByCurve`.
Проёмы: `CutOpening` (окно/дверь/заложенный проём), `CreateHostedFamily`.
Семейства: `LoadFamily`, `PlaceFamilyInstance`, `SetInstanceParameters`.
Кровля/стропила: `CreateRoof`, `CreateRafter` (как отдельные операции, проект-специфичные — могут быть в модуле проекта).
Отчётность: `CollectCounts`, `ExportCountsJson`.

### 4.3. Идемпотентность

- Операция должна уметь определить, что сущность уже создана (по уникальным именам/меткам/параметрам), и не дублировать. Механизм: тег в `Comments`/параметре `ADSK_...` или отдельный реестр созданных Id в JSON-состоянии проекта.
- Повторный прогон с тем же JSON → модель идентична (сравнение по counts/ids).

## 4. Требования к стандарту хранения данных (JSON)

### 4.1. Версионирование

- Корневое поле `schema_version` (semver, например `"1.0.0"`). Изменение схемы → подъём версии + миграция.
- `project` (метаданные: имя, адрес, фаза, автор, дата).
- `units` (единицы входных данных: мм, градусы; ядро конвертирует).
- `source` (provenance: файл-источник, хэш, версия инструмента).

### 4.2. Структура здания (минимальный набор)

```
{
  "schema_version": "1.0.0",
  "project": { "name": "...", "phase": "...", "author": "..." },
  "units": { "length": "mm", "angle": "deg" },
  "levels": [ { "name": "Уровень 1", "elevation_mm": 0 }, ... ],
  "grids": [ { "name": "1", "start": [x,y], "end": [x,y] }, ... ],
  "wall_types": [ { "name": "Наружная 500", "structure": [ { "material": "...", "thickness_mm": 250 }, ... ] } ],
  "walls": [ { "type": "Наружная 500", "start_mm": [x,y], "end_mm": [x,y], "height_level": "Уровень 2", "base_level": "Уровень 1", "flipped": false } ],
  "families": [ { "family": "Окно", "type": "Окно 1.2x1.5", "host_wall": "<wall id>", "position_mm": [x,y,z], "parameters": { "Ширина": 1200 } } ],
  "openings": [ { "host_wall": "<wall id>", "kind": "window|door|blocked", "width_mm": 1200, "height_mm": 1500, "sill_mm": 900, "position_mm": [x,y] } ],
  "defects": [ { "element": "<id>", "description": "...", "severity": "info|warn|error" } ]
}
```

- Идентификаторы сущностей — строковые ключи внутри JSON (не Revit ElementId), чтобы быть независимыми от модели.
- Ссылки между сущностями — по этим ключам (wall → wall_type по имени, opening → wall по id).
- Координаты — в мм (человекочитаемо), ядро конвертирует.

### 4.3. Валидация

- JSON Schema (или аналог) для валидации при загрузке.
- Обязательные поля, типы, диапазоны (высота > 0, толщина > 0).
- Проверка ссылочной целостности (wall.type существует в wall_types).
- Отчёт об ошибках с путями (JSONPath) и понятными сообщениями.

### 4.4. Round-trip

- `Export`: модель → JSON (счётчики, координаты, типы). Используется для верификации и снимков.
- `Import`: JSON → модель через операции.
- Сравнение `Export(Import(json))` с исходным json (нормализованно) — критерий корректности.

## 5. Структура проекта (предлагаемая)

```
RevitBimCore/                  # ядро (библиотека, net48/net6+)
  Core/                        # абстракции, транзакции, единицы, логгер
  Services/                    # LevelService, WallService, FamilyService, ...
  Operations/                  # IOperation, базовые операции
  Mapping/                     # JSON DTO, мапперы, валидаторы
  Tests.Unit/                  # чистые юнит-тесты (без Revit)
  Tests.Integration/           # Nice3point-тесты (в Revit)

Projects/
  K1Library/                   # проект: данные + скрипты + тесты
    data/K1_library_linked.json
    scripts/build.py (или .cs)
    tests/
  KorpusFans/                  # вентиляторы (может быть только DWG, но JSON-описание)
  MkD11/                       # МКД 11-этажный
  ...

Shared/
  schemas/                     # JSON Schema для валидации
  templates/                   # шаблоны проектов (rte, семейства)
```

Принцип: ядро и операции — общие; проекты — данные + тонкие скрипты-оркестраторы.

## 6. Вопросы для облачного ИИ (на которые нужно ответить)

### Архитектура

1. **Граница ядра и Revit API**: как лучше изолировать Revit API для тестируемости — интерфейсы-обёртки (адаптер) или внедрение зависимостей через фабрики? Какой паттерн (Repository/Service/Command) выбрать для операций?
2. **Транзакции**: одна транзакция на всю операцию или вложенные? Как обрабатывать частичный провал (rollback vs. сохранение успешной части)? Нужны ли компенсирующие транзакции?
3. **Идемпотентность**: какой механизм надёжнее для Revit — метки в параметрах элементов, отдельный реестр Id в JSON-состоянии, или поиск по геометрии/имени? Как избежать коллизий при повторном прогоне?
4. **Расширяемость**: как регистрировать новые операции/проекты — DI-контейнер, реестр по атрибутам, плагинная модель (Assembly.Load)? Какой уровень изоляции проектов (отдельные сборки vs. одна сборка с папками)?
5. **Версионирование ядра**: как версионировать Core и Operations независимо от проектов? SemVer, breaking changes, миграции данных.

### Данные

6. **JSON-схема**: один корневой документ на здание или набор файлов (уровни отдельно, стены отдельно)? Как балансировать читаемость и атомарность?
7. **Координаты**: мм во входе — ок, но как хранить повороты/ориентацию стен, криволинейные стены, дуги? Как представлять отверстия в стенах (host + параметры vs. отдельные элементы)?
8. **Типы стен**: как описывать многослойную структуру (материал, толщина, функция, приоритет) и маппить на Revit WallType? Нужен ли кэш/реестр типов?
9. **Семейства**: как описывать загрузку семейств (путь к .rfa, имя типа, параметры по умолчанию) и размещение экземпляров? Как обрабатывать отсутствующие семейства?
10. **Round-trip**: насколько полным должен быть экспорт (все параметры или только созданные ядром)? Как сравнивать модели (по Id, по геометрии, по counts)?
11. **Валидация**: JSON Schema достаточно или нужна кастомная валидация с бизнес-правилами (например, стена не может быть короче 100 мм)? Где живут правила — в ядре или в схеме?
12. **Миграции**: как мигрировать старые JSON (K1_library.json → v1.0.0) при изменении схемы? Инструмент миграции в ядре или отдельный?

### Тестирование

13. **Пирамида тестов**: сколько юнит vs. интеграционных? Как тестировать геометрию без Revit (моки точек)?
14. **Тестовые данные**: где хранить эталонные JSON/модели? Как обновлять эталоны при изменении схемы (golden files)?
15. **CI**: можно ли запускать интеграционные тесты в CI без Revit (контейнер/виртуальная машина)? Если нет — как структурировать, чтобы CI проверял хотя бы логику?
16. **Регрессия**: как отслеживать, что изменение ядра не сломало существующие проекты (K1, МКД)?

### Интеграция с существующим

17. **DwgParser/AccCore**: как связать JSON-стандарт с DWG (экстракция полилиний/блоков → JSON → стены)? Нужен ли отдельный маппер DWG→JSON?
18. **DesignBase**: как использовать ядро для извлечения данных из моделей (экспорт → JSON → RAG)? Какие данные нужны для поиска (тексты, счётчики, геометрия)?
19. **Revit API версии**: поддержка нескольких версий Revit (2024/2025/2026) — мульти-таргетинг или одна версия? Как абстрагировать различия API?
20. **Семейства и шаблоны**: где хранить .rfa/.rte (в репозитории, в общем хранилище, по URL)? Как версионировать?

## 8. Ограничения и не-цели

- Не переписывать существующие проекты целиком за один раз — инкрементальная миграция.
- Не создавать GUI/плагин для Revit (только headless-тесты и скрипты) на первом этапе.
- Не менять формат хранения существующих DWG/DXF — только добавлять JSON-слой.
- Ядро не должно зависеть от конкретных проектов (K1, коровники и т.д.).
- Не использовать платные библиотеки без согласования.

## 9. Критерии приёмки

- [ ] Новый проект (например, «Коровник №4») можно добавить, создав только папку с JSON-данными и тонким скриптом, без изменения ядра.
- [ ] Повторный прогон с тем же JSON не создаёт дублей (идемпотентность).
- [ ] Юнит-тесты логики проходят без Revit.
- [ ] Интеграционные тесты проходят в Revit и проверяют создание ожидаемых сущностей.
- [ ] JSON валидируется по схеме с понятными ошибками.
- [ ] Round-trip Export(Import(json)) ≡ json (нормализованно).
- [ ] Документация: README ядра, пример проекта, гайд по добавлению нового проекта.
